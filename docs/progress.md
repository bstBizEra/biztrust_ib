# Project progression

**Snapshot:** 1 October 2026 · **Version:** 0.2.0 · **Release boundary:** local demonstration

This is the project's human-readable status page and the shared update point for agents. It tracks deliverables and evidence; it does not grant approval to deploy, publish real products, handle live payments, or issue coverage. The baseline below is drawn from the repository's existing documentation and source as of this date. It is not a fresh test run or live-provider acceptance.

Open the [HTML progress board](progress.html) for the visual view. This Markdown file remains the source for milestones and evidence; run `npm run progress:build` after changing it. `npm run progress:check` detects an out-of-date HTML board and runs in the project verification gate.

The [backend and domain plan](implementation-plan.md) supplements the roadmap on this page with backend transaction boundaries, all 15 BIZTRUST-IB-ARCH-001 domains and production acceptance gates displayed on the board. It records planned delivery, not completed domains. Dates and estimates remain unset until owners confirm capacity and external dependencies.

The [repository reuse plan](repository-reuse.md) and its [structured register](repository-plan.json) map upstream packages, services and engineering references to these phases and modules. Existing dependencies are distinguished from proposed additions; each item records integration, acceptance and fork/clone policy. No new dependency or service is activated by this plan.

## How to update this page

Agents and humans should update this file in the same change as work that affects a milestone. Keep one row per outcome and retain its ID. Add a row when a new outcome cannot fit an existing one. Do not turn an undocumented claim into **Verified**; link to a test report, review record, acceptance document or exact source change and state its environment. For an external dependency, name the owner role and the artifact needed. Use **In progress** for partially implemented work, and keep a blocker visible until its owner supplies evidence.

Add a short entry to [progress updates](progress-updates.md) for every status or scope change. Link the relevant milestone ID, summarize what changed, identify evidence and remaining limits. Update the snapshot date when changing the table. If a test or provider check fails, record the failure and move the affected milestone back to **In progress** or **Blocked** as appropriate. Do not silently erase previous evidence or rewrite older update entries.
